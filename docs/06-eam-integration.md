    # Интеграция данных EAM

Как данные корпоративной архитектуры (EAM) попадают в граф: какие объекты забираем, как читаем API, как сопоставляем с каноническими узлами [00-vision.md](00-vision.md). Источник контракта — [`eam-api.yaml`](eam-api.yaml) (OpenAPI 3.0.3, «EAM Tool API», версия 0.4). В PoC EAM представлен заглушкой (`StubSources.eam`), реальный контракт не проверен ([production gap 3.5](05-production-gap-list.md)).

## Что нужно из EAM

| Сущность EAM | Endpoint | Канонический узел | Статус в коде |
|---|---|---|---|
| ИТ-платформа (IT Platform) | `/api/platforms/` | `Platform` | в vision есть, в `canonical-model` пока нет |
| ИТ-решение (IT Solution) | **не подтверждён** (см. [открытые вопросы](#открытые-вопросы)) | `Solution` | в vision есть, в `canonical-model` пока нет |
| ИТ-система (IT System) | `/api/itsystems/` | `ITSystem` | есть (`ITSystem`, мастер — EAM) |

Связи между ними, как в vision:

```text
(ITSystem)-[:USES_SOLUTION]->(Solution)
(Solution)-[:USES_PLATFORM]->(Platform)
```

Из этого следует транзитивная цепочка `ITSystem → Solution → Platform`: «на каких платформах работает система» и «какие системы заденет изменение платформы» — два обхода в 2 перехода. `USES_SOLUTION` и `USES_PLATFORM` нужно добавить в `RelationType` и authority matrix (мастер — EAM); `Solution` и `Platform` — в `NodeLabel`/`NodeData`, с ключом уникальности `gid` как у остальных узлов.

## Устройство EAM API

EAM — **метамодельная** система: все типы объектов обслуживаются одинаковыми endpoint-ами, а набор полей типа задаётся данными, не схемой OpenAPI.

- Для каждого типа есть один и тот же набор операций: `GET /api/<type>/`, `GET|PATCH /api/<type>/{id}/`, `POST …/archive/`, `…/draft/`, `…/select2/`. Типов в спеке ~60 (платформы, ИТ-системы, компании, сотрудники, бизнес-способности, стандарты и т. д.); для интеграции нужны только три.
- Все ответы — `ArchObject`: `{id: int, ver: int, datetime, attrs: <свободный объект>}`. **Схема `attrs` в OpenAPI не описана.** Реальные поля (в том числе поля-ссылки на другие объекты) определяются метаданными типа: `GET /api/types/{id}/`, `GET /api/types/{id}/options/?kind=fields|groups|computed|system`, а также типами `type_fields`, `type_groups`, `type_computed`.
- Связи между объектами — **поля-ссылки внутри `attrs`**, а не отдельные ресурсы. Это подтверждает описание `select2`: фильтр `filter_field`/`filter_value` работает «только для полей ссылок, заявленных в схемах типов». Отдельный ресурс связи (`/api/mrelations/`) в спеке есть, но его семантика из спеки не ясна; не использовать, пока не выяснено.
- Системные вычисляемые поля: `eam_id`, `eam_name`, `eam_permalink` (`options?kind=system`).

### Чтение

| Параметр списка | Назначение |
|---|---|
| `page`, `page_size` | Постраничность. Ответ — **голый массив** `ArchObject[]`, без `total`/`next`: конец определяем по неполной (или пустой) странице |
| `sort` | `поле`, `-поле`, список через запятую; допустимы колонки `id`, `ctime`, `mtime` и поля схемы |
| `fields` | Какие `attrs` вернуть (список через запятую) — нужно, чтобы не качать лишнего |
| `enrich=1` | Серверное обогащение (содержимое не описано; для сырых ссылок не включать, см. ниже) |
| `search`, `search_by`, `search_mode` | Поиск; для синхронизации не нужен |

`GET /api/<type>/{id}/` принимает `fields` и `enrich`; в описании упоминается выбор версии, но параметр версии в спеке не объявлен — уточнить.

Фильтра «изменено после T» в спеке **нет**. Есть сортировка по `mtime`.

### Аутентификация

Три схемы: `basicAuth`, `cookieAuth` (`sessionid`), `tokenAuth` (заголовок `Authorization: Token <…>`). Для сервисной интеграции — `tokenAuth`. `POST /api/auth/token/` выдаёт персональный токен залогиненного пользователя, идемпотентно; нужна отдельная read-only учётная запись для адаптера, токен в Docker secret (как остальные секреты стенда).

### Запись и согласование (не используем)

`POST`, `PATCH`, `draft`, `archive` кладут изменения в **буфер** согласования (`/api/buffers/`, состояния вроде `verified`) для не-администраторов; в основном состоянии объект меняется только после утверждения. Архивирование — тоже предложение с маркером `to_archive`. Для нас важно следствие: **граф должен читать только основное состояние (`/api/<type>/`), не буферы** — иначе в витрину попадут неутверждённые данные. Адаптер EAM — read-only, мутирующие методы не вызывает.

В спеке есть `/api/mcp/` (JSON-RPC 2.0, read-only MCP-сервер EAM). Для синхронизации не используем: нам нужны полные детерминированные снимки с пагинацией, а не диалоговые инструменты.

## Схема синхронизации

В спеке нет webhook-ов и нет фильтра по времени изменения, поэтому:

1. **Основной путь — polling.** Адаптер опрашивает три endpoint-а по `sort=-mtime` и идёт страницами, пока не встретит объект с уже известным `(id, ver)`.
2. **Snapshot для reconcile.** Периодически (и при replay/rebuild через админский эндпоинт ingestion-сервиса) читается полный список каждого типа. Это же единственный способ обнаружить **удаление/архивацию**: в спеке нет tombstone-событий, объект просто пропадает из основного списка (или меняет состояние — проверить). Пропавший `id` → `TombstoneSourceRecord`.
3. **Событие и идемпотентность.** Один объект EAM — одна запись в journal: `source = EAM`, `sourceType ∈ {PLATFORM, SOLUTION, IT_SYSTEM}`, `sourceId = id` (без префикса, решение владельца 2026-10-04), `sourceVersion = ver`, `contentHash` — sha256 от канонизированного `attrs`. Повторное получение той же `ver` с тем же hash — no-op. `datetime` из `ArchObject` использовать как время изменения источника, а не как время получения.
4. Сырой ответ сохраняется в raw-хранилище (S3) до нормализации, как у остальных адаптеров.

Webhook-путь заглушки на реальный EAM не переносится, пока EAM не умеет их отправлять. Предел свежести — интервал polling; как показали замеры ([04-poc-measurements.md](04-poc-measurements.md)), p95 «источник → граф» упирается в этот интервал.

## Нормализация и связи

Нормализатор превращает `ArchObject` в `UpsertNode`/`UpsertRelation` (`GraphCommand`):

| Источник | Команда |
|---|---|
| объект платформы | `UpsertNode(Platform{name, type, version})` |
| объект решения | `UpsertNode(Solution{name, lifecycle, description})` |
| объект ИТ-системы | `UpsertNode(ITSystem{name, status, criticality, description})` |
| поле-ссылка ИТ-системы → решение | `UpsertRelation(USES_SOLUTION)` |
| поле-ссылка решения → платформа | `UpsertRelation(USES_PLATFORM)` |

Правила:

- **Ссылка = id объекта EAM.** Целевой узел ищется по crosswalk `(EAM, sourceType, id)`. Если цель ещё не загружена (порядок чтения разный), команда откладывается `DeferRelation` и разрешается при появлении цели — порядок опроса типов не должен влиять на результат.
- **Исчезновение ссылки в `attrs` = закрытие связи**, не удаление узлов: `CloseAssertion` для соответствующего утверждения источника.
- **Критичность и статус** — свободные значения EAM; значения словаря сопоставляются с `Criticality` (`ITSystem`) через явную таблицу, неизвестные значения не отбрасываются, а сохраняются в `status` и помечаются для разбора.
- **Authority.** Для `ITSystem`, `Solution`, `Platform` и связей между ними мастер — EAM; `ITSystem.criticality` обновляет только EAM. Остальные источники (SCM и др.) могут ссылаться на систему по EAM-ключу, но не меняют эти узлы.
- **Identity.** Ключ — `(EAM, sourceType, id)`. Имя (`name`) не ключ: совпадение имён разных сущностей и переименования обычны. Совпадения с другими источниками (например, `systemCode` в SCM) — через crosswalk и candidate matching.

## Открытые вопросы

Эти пункты нельзя вывести из `eam-api.yaml`; их нужно закрыть до реализации реального адаптера (и зафиксировать в контрактных тестах).

1. **Где в EAM «ИТ-решение»?** Среди ~60 типов нет endpoint-а с очевидным именем `solutions`. Кандидаты по названиям — `itproducts`, `msys`, `okita`, `aknsd`; это догадки, а не факты. Нужны: имя типа и `typeurl`.
2. **Имена и типы полей `attrs`** для трёх типов: ключ имени, статус, критичность, словари значений, и главное — **какие поля являются ссылками** и на какой тип (получить через `/api/types/{id}/options/?kind=fields`).
3. **Кратность ссылок:** одна платформа на решение или список; хранится ли ссылка в «прямом» поле одной стороны или в обеих.
4. **Что возвращает основной список для архивных объектов** (скрыты, помечены атрибутом, остаются). От этого зависит логика tombstone.
5. **Версионирование:** объявлена ли выборка по версии `GET /{id}/` (в описании есть, параметра нет); всегда ли растёт `ver` при изменении `attrs`.
6. **Лимиты:** максимальный `page_size`, rate limit, стабильность порядка при `sort=-mtime` во время записи (риск пропусков при сдвиге страниц — компенсируется периодическим snapshot).
7. **Семантика `enrich` и `mrelations`/`mobjects`**: нужны ли они для получения связей.
8. **Права:** какими правами должен обладать сервисный пользователь, чтобы видеть все объекты трёх типов, но не буферы.

## Тестирование

- Контрактный тест адаптера по записанным ответам (`ArchObject` страниц трёх типов + метаданные типов); ожидаемые `GraphCommand` сравнивать по значению.
- Сценарии: пагинация (последняя страница пустая и неполная), повтор той же `ver` (no-op), смена ссылки (закрытие старой связи и открытие новой), ссылка на ещё не загруженный объект (`DeferRelation`), пропажа объекта из списка (tombstone), одинаковое `name` у разных `id`.
- Заглушка `StubSources.eam` расширяется типами `PLATFORM`/`SOLUTION` и ссылками, чтобы вертикальный срез `ITSystem → Solution → Platform` проверялся приёмочным тестом вместе с остальным графом.
