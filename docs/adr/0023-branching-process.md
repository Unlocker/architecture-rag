# 0023. Процесс: `develop → epic/<parent> → feature/<child>`; вливает архитектор, в `develop` — владелец

- **Статус:** Принято
- **Дата:** 2026-10-03
- **Источник:** владелец 2026-10-03; [`01-development-order.md`](../01-development-order.md)
- **Кто принял:** владелец

## Контекст

Несколько разработчиков-агентов ведут подзадачи параллельно, нужна предсказуемая интеграция и контроль.

## Решение

Epic-ветка создаётся от `develop` при старте фичи, подзадачи ведутся в `feature/<KEY>` от epic. PR подзадачи открывается в epic как draft. В epic вливает архитектор после ревью без блокирующих находок и зелёного CI. `epic → develop` — только по поручению владельца.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| Epic-ветки и draft PR | Изоляция фичи, контроль владельца | Больше слияний | Выбран |
| Все PR в `develop` | Проще | Нет изоляции незавершённых фич | Отклонён |

## Последствия

- **Положительные:** Понятная ответственность на каждом шаге.
- **Отрицательные / ограничения:** Epic нужно обновлять из `develop`.
