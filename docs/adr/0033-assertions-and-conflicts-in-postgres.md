# 0033. Утверждения и конфликты источников хранятся в PostgreSQL, в граф попадают только имена свойств

- **Статус:** Принято
- **Дата:** 2026-10-13
- **Источник:** UNLOCKER-278; кандидат К-2 в `_reversa_sdd/adrs/candidates.md` (UNLOCKER-269); согласие владельца в UNLOCKER-260 (2026-10-13); реализация — UNLOCKER-175
- **Кто принял:** владелец, 2026-10-13

## Контекст

ADR [0008](0008-authority-matrix-field-level.md) обещает, что конфликты разбираются по явным правилам. ADR [0030](0030-deployment-system-conflict.md) и [0031](0031-it-system-platform-invariant.md) расширяют таблицу `source_conflict`, но само решение «где и как хранятся утверждения и конфликты» в реестре отсутствовало: оба ADR молча на него опираются.

## Решение

1. **Утверждения** каждой записи хранятся в таблице `property_assertion` (PostgreSQL) с флагом `authoritative`, который берётся из `AuthorityMatrix`. Утверждения записи заменяются целиком (`DELETE` + `INSERT`) до транзакции Neo4j (`ingestion/identity-resolution/.../PostgresSourceConflicts.java:36-40`).
2. **Конфликт** — пара «авторитетное утверждение / неавторитетное с другим значением» для одного `gid` и свойства; значения сравниваются точным равенством строк (`PostgresSourceConflicts.java:44-47`, `:112`). Хранится в `source_conflict` (миграция `V5__source_conflict.sql`; поле `kind` добавлено в `V7__source_conflict_kind.sql`). Без авторитетного утверждения конфликтов нет.
3. **Строки конфликтов не удаляются:** они переходят `OPEN` ↔ `RESOLVED` (`PostgresSourceConflicts.java:49-66`). Canonical-значение конфликт не меняет, его выбирает проектор (`SourceConflicts.java:10-18`).
4. **Конфликт вычисляется по утверждениям всех записей `gid`, а не по состоянию графа**, поэтому результат не зависит от порядка прихода мастера и неавторитетного источника.
5. **В граф попадают только имена** конфликтующих свойств: `ASSERTS.conflicts` на рёбрах узла `gid` (`GraphProjector.java:468-488`, вызов — `:356`). Значения остаются в PostgreSQL: значения из источников недоверенные, а граф читают агенты.
6. **Известное окно рассогласования.** PostgreSQL обновляется до транзакции Neo4j, общей транзакции нет. Между ними конфликт уже существует в `source_conflict`, а маркера в графе ещё нет. Это ограничение 1 ADR 0030/0031; оно принято для PoC.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| A. Утверждения и конфликты в PostgreSQL, в граф — имена свойств | Значения источников не попадают в граф; результат не зависит от порядка прихода | Две системы хранения без общей транзакции | Выбран |
| B. Конфликт — узел в Neo4j | Одна система хранения | Значения источников попали бы в граф, который читают агенты | Отклонён |
| C. Вычислять конфликт на лету из `SourceRecord` | Нет таблиц | Зависит от порядка прихода; нет истории `OPEN`/`RESOLVED` | Отклонён |

## Последствия

- **Положительные:** история конфликтов сохраняется (`RESOLVED` вместо удаления); ADR 0030/0031 опираются на явное решение.
- **Отрицательные / ограничения:** окно рассогласования PostgreSQL ↔ граф (п. 6); сравнение по точному равенству строк не нормализует значения.
- **Затронутый код:** `ingestion/identity-resolution` (`SourceConflicts`, `PostgresSourceConflicts`, миграции V5, V7), `ingestion/graph-projector` (`GraphProjector`), `access/admin-console` (`ConsoleReadRepository` читает `source_conflict`).
