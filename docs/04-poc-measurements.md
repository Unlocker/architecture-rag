# Замеры PoC (критерий готовности 9)

Результаты прогона `platform/docker/scripts/measure.sh` на демо-стенде и методика. Цифры — **ориентир для PoC, а не SLO**: стенд на одной машине, источники — заглушки, граф крошечный (см. «Ограничения»). Пробелы относительно production — в [`05-production-gap-list.md`](05-production-gap-list.md).

Интервал polling не менялся (30 с).

## Методика

Все шаги выполняет `measure.sh`; на хосте нужны Docker, bash и python3 (только стандартная библиотека). Запросы идут так же, как у агента: через TLS-proxy, с токеном `client_credentials` из Keycloak. Prometheus читается изнутри контейнера (`docker compose exec prometheus wget`), порты наружу не открываются.

1. **MCP tools.** Список берётся из `tools/list`. Для каждого tool с фиксированными аргументами из seed (`EAM-1042`): 3 прогревочных вызова (не входят в статистику), затем `K` вызовов последовательно и `K` вызовов в `P` потоках. Клиентские p50/p95/max включают TLS, proxy, проверку JWT и Neo4j. Для сравнения берётся p95 из Prometheus: `histogram_quantile(0.95, sum by (le, tool) (increase(archrag_mcp_tool_call_milliseconds_bucket[<окно прогона>])))`. Он меньше клиентского, потому что меряет только выполнение tool на сервере, а корзины гистограммы грубые (`ping` показывает 1 мс как нижнюю границу корзины).
2. **Источник → граф.** Два режима (`E2E_PATH=webhook|poll|both`), по `N` замеров в каждом. В обоих `POST /control/upsert` в `stub-eam` с уникальным именем объекта `EAM-1042`, затем опрос `get_asset` (каждые 0,25 с) до появления нового имени; время считается на клиенте от ответа заглушки до появления значения в графе; p50/p95/max по `N`. Если значение не появилось за 300 с — провал.
   - `webhook`: upsert без задержки; заглушка шлёт адаптеру подписанный webhook напрямую (внутри сети `edge`, мимо TLS-proxy; демо-допущение), в ответе проверяется `webhookStatus` 2xx. Порог p95 — 30 с, это гейт критерия 2.
   - `poll`: перед upsert пауза случайной длины от 0 до интервала polling (равномерная фаза цикла адаптера), в теле `"notify": false` — webhook не отправляется. Порог p95 — интервал polling + 5 с, это оценка страховки.
   Burst из раздела 3 всегда идёт с `"notify": false`: его сценарий не менялся относительно #59. Если за webhook следом приходит polling с той же версией, конвейер отбрасывает дубль (`DUPLICATE`/`IGNORED_OLD_VERSION`); замер берёт время первого появления в графе.
3. **Throughput и sync lag.** Пачка из `M` upsert в `stub-eam` (новые объекты `EAM-LOAD-<id>-NNNNN`), затем ожидание, пока все события пачки не станут `PROJECTED` в `inbox_event`. Throughput — число событий пачки, делённое на интервал от `min(received_at)` до `max(updated_at)` по ним. Sync lag — `max(archrag_ingestion_sync_lag_seconds)`, семплируется раз в 2 с во время ожидания и берётся `max_over_time` за прогон.
4. **Error и DLQ rate.** `increase(archrag_ingestion_events_total[окно])` по label `status`; доля не-`PROJECTED`; `archrag_ingestion_dlq_open` и число `QUARANTINED` в `inbox_event` до и после; ошибки tools считаются на клиенте (JSON-RPC `error` или `isError`).
5. **Глубина traversal.** `trace_dependencies` от `EAM-1042` (направление `downstream`) при `maxDepth` = 1…6, 7, 0 и без параметра; по 5 вызовов, p50, число узлов, путей, связей и признак `truncated`.

Скрипт завершается с кодом 1, если p95 «источник → граф» выше порога своего пути, вырос DLQ или `QUARANTINED`, любой tool вернул ошибку, либо значение вне диапазона глубины принято.

## Ограничения глубины и бюджета

Значения из `access/mcp-server/src/main/resources/application.yml`:

| Ограничение | Значение | Поведение при превышении |
|---|---|---|
| Глубина (`max-depth`) | 6 | `maxDepth` вне 1…6 — ошибка валидации, clamp не выполняется; обход без верхней границы запрещён |
| Узлов (`max-nodes`) | 500 | ответ усекается, `truncated=true` |
| Путей (`max-paths`) | 50 | `truncated=true`; при усечении состав путей может отличаться между вызовами |
| Таймаут запроса (`timeout`) | 5 с | tool возвращает ошибку «timed out»; на холодном стенде первые вызовы под нагрузкой хоста иногда упирались в него — поэтому в замерах есть прогрев |
| Размер ответа (`max-response-bytes`) | 512 КБ | усечение |

В демо-графе от самого глубокого seed-актива достижимо 6 узлов и 5 путей, поэтому бюджеты узлов и путей не срабатывают (`truncated=false` на всех глубинах); глубина больше 3 ничего не добавляет. Срабатывание бюджетов проверяют интеграционные и приёмочные тесты (F3), а не этот замер. Замер глубины показывает только, что latency не растёт с `maxDepth` на графе такой формы; на реальном графе это нужно перемерить.

## Выводы

- **Критерий 2.** Принято решение владельца (вариант (а) с формулировкой (в)): p95 «источник → граф» меряется по webhook-пути, порог 30 с; результат 2,1 с. Polling остаётся страховкой с отдельной оценкой: p95 28,6 с при пороге «интервал + 5 с» = 35 с. Вариант (б) (снижение интервала polling) отклонён, интервал не менялся. Формулировка критерия обновлена в `docs/00-vision.md`. Webhook идёт заглушка → адаптер напрямую внутри `edge`: путь через внешний TLS-proxy в замер не входит.
- **Throughput.** ≈ 3,4 события/с на загруженном общем хосте (в #59 было 1,4 при более высокой нагрузке хоста) — это разбор очереди одним `ingestion`; во время burst sync lag вырос до 24 с и вернулся к нулю. Для объёма «десятки тысяч активов» первичная загрузка займёт часы, поэтому для production нужен Kafka и параллельные потребители (gap list, п. 1.4). Проекция на целевой объём — оценка по этому одному числу, не замер.
- **Tools.** p95 в диапазоне 0,13–0,43 с на крошечном графе — запас большой, но на реальном графе и без шума от соседнего стенда цифры будут другими.
- **Надёжность.** Ошибок обработки, DLQ и `QUARANTINED` за прогон нет; 0 ошибок из 1200 вызовов tools.

## Ограничения замеров

- Общий хост: load average ≈ 11–20 на 8 ядрах. Первые вызовы к холодному Neo4j упирались в таймаут запроса 5 с (поэтому в скрипте есть прогрев); в замеры они не входят.
- Граф — seed заглушек плюс 200 объектов burst; формы реального графа (степени узлов, глубина) нет.
- `N=20` даёт грубую оценку p95 (это по сути второе по величине значение); по polling p95 28,6 с близок к интервалу, но порог 35 с выдерживается с запасом.
- Webhook-путь не проходит через TLS-proxy и не включает ретраи заглушки.
- Клиентский p95 включает TLS-рукопожатия и OIDC-проверку и больше серверного p95 из Prometheus.

## Как повторить

```bash
cd platform/docker
./smoke.sh                                  # стенд поднят с профилем observability, проверки зелёные
scripts/measure.sh | tee measure.md         # N=20 M=200 K=100 P=4 E2E_PATH=both по умолчанию
E2E_PATH=webhook scripts/measure.sh         # только webhook-путь (гейт критерия 2), несколько минут
N=3 M=20 K=10 E2E_JITTER_MAX=2 scripts/measure.sh   # быстрый прогон для проверки скрипта
```

Режим `poll` занимает около `N` × (интервал / 2 + интервал / 2) ≈ 10 минут при `N=20`, весь `measure.sh` с параметрами по умолчанию — около 18 минут. Код возврата 1 означает, что порог своего пути не выдержан или был сбой; детали — в разделе «Провалы» вывода.
