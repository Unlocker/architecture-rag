# Замеры PoC (критерий готовности 9)

Результаты прогона `platform/docker/scripts/measure.sh` на демо-стенде и методика. Цифры — **ориентир для PoC, а не SLO**: стенд на одной машине, источники — заглушки, граф крошечный (см. «Ограничения»). Пробелы относительно production — в [`05-production-gap-list.md`](05-production-gap-list.md).

## Итог

| Проверка | Результат |
|---|---|
| p95 latency tools | 0,5–0,7 с последовательно, 0,4–1,2 с при 4 параллельных потоках (клиентские замеры через TLS-proxy и OIDC) |
| p95 «источник → граф» (критерий 2, порог ≤ 30 с) | **30,8 с — порог не выдержан**, повторный прогон дал 31,0 с. Задержка равномерно лежит в диапазоне 2–32 с и определяется интервалом polling адаптера (30 с) плюс 1–2 с обработки |
| Throughput ingestion | ≈ 1,4 события/с на стенде (200 событий за 144 с) |
| Sync lag | максимум 91,8 с во время burst из 200 событий (очередь разбирается последовательно), 0 с после опустошения очереди |
| Error / DLQ rate | 0 из 222 событий не в `PROJECTED`; `archrag_ingestion_dlq_open` и `QUARANTINED` не выросли; 0 ошибок из 1000 вызовов tools |
| Глубина `trace_dependencies` | `maxDepth` 1…6 принимается, 7 и 0 отклоняются ошибкой `maxDepth must be in 1..6` (без clamp); без `maxDepth` действует лимит 6 |

**Порог 30 с на этой конфигурации не выдерживается.** Это не случайный выброс, а следствие дизайна стенда: единственный путь «источник → граф» — polling раз в 30 с, а webhook-путь заглушки в замере не используется. Любое изменение, попавшее сразу после опроса, ждёт почти весь интервал, и p95 при равномерной фазе неизбежно упирается в 30 с + время обработки. Интервал мы не подкручивали ради цифры; варианты решения — в разделе «Выводы».

## Методика

Все шаги выполняет `measure.sh`; на хосте нужны Docker, bash и python3 (только стандартная библиотека). Запросы идут так же, как у агента: через TLS-proxy, с токеном `client_credentials` из Keycloak. Prometheus читается изнутри контейнера (`docker compose exec prometheus wget`), порты наружу не открываются.

1. **MCP tools.** Список берётся из `tools/list`. Для каждого tool с фиксированными аргументами из seed (`EAM-1042`): 3 прогревочных вызова (не входят в статистику), затем `K` вызовов последовательно и `K` вызовов в `P` потоках. Клиентские p50/p95/max включают TLS, proxy, проверку JWT и Neo4j. Для сравнения берётся p95 из Prometheus: `histogram_quantile(0.95, sum by (le, tool) (increase(archrag_mcp_tool_call_milliseconds_bucket[<окно прогона>])))`. Он меньше клиентского, потому что меряет только выполнение tool на сервере, а корзины гистограммы грубые (`ping` показывает 1 мс как нижнюю границу корзины).
2. **Источник → граф.** `N` раз: пауза случайной длины от 0 до интервала polling (чтобы равномерно выбрать фазу цикла адаптера), `POST /control/upsert` в `stub-eam` с уникальным именем объекта `EAM-1042`, затем опрос `get_asset` (каждые 0,25 с) до появления нового имени. Время считается на клиенте от ответа заглушки до появления значения в графе; p50/p95/max по `N` замерам. Если значение не появилось за 300 с — провал.
3. **Throughput и sync lag.** Пачка из `M` upsert в `stub-eam` (новые объекты `EAM-LOAD-<id>-NNNNN`), затем ожидание, пока все события пачки не станут `PROJECTED` в `inbox_event`. Throughput — число событий пачки, делённое на интервал от `min(received_at)` до `max(updated_at)` по ним. Sync lag — `max(archrag_ingestion_sync_lag_seconds)`, семплируется раз в 2 с во время ожидания и берётся `max_over_time` за прогон.
4. **Error и DLQ rate.** `increase(archrag_ingestion_events_total[окно])` по label `status`; доля не-`PROJECTED`; `archrag_ingestion_dlq_open` и число `QUARANTINED` в `inbox_event` до и после; ошибки tools считаются на клиенте (JSON-RPC `error` или `isError`).
5. **Глубина traversal.** `trace_dependencies` от `EAM-1042` (направление `downstream`) при `maxDepth` = 1…6, 7, 0 и без параметра; по 5 вызовов, p50, число узлов, путей, связей и признак `truncated`.

Скрипт завершается с кодом 1, если p95 «источник → граф» больше 30 с, вырос DLQ или `QUARANTINED`, любой tool вернул ошибку, либо значение вне диапазона глубины принято. Поэтому приведённый ниже прогон завершился с кодом 1.

## Ограничения глубины и бюджета

Значения из `access/mcp-server/src/main/resources/application.yml`:

| Ограничение | Значение | Поведение при превышении |
|---|---|---|
| Глубина (`max-depth`) | 6 | `maxDepth` вне 1…6 — ошибка валидации, clamp не выполняется; обход без верхней границы запрещён |
| Узлов (`max-nodes`) | 500 | ответ усекается, `truncated=true` |
| Путей (`max-paths`) | 50 | `truncated=true`; при усечении состав путей может отличаться между вызовами |
| Таймаут запроса (`timeout`) | 5 с | tool возвращает ошибку «timed out»; на холодном стенде первые вызовы под нагрузкой хоста иногда упирались в него — поэтому в замерах есть прогрев |
| Размер ответа (`max-response-bytes`) | 512 КБ | усечение |

В демо-графе от самого глубокого seed-актива достижимо 6 узлов и 5 путей, поэтому бюджеты узлов и путей не срабатывают (`truncated=false` на всех глубинах); глубина больше 3 ничего не добавляет. Срабатывание бюджетов проверяют интеграционные и приёмочные тесты (F3), а не этот замер. Замер глубины показывает только, что latency не растёт с `maxDepth` на графе такой формы; на реальном графе это нужно перемерить.

## Выводы

- **Порог 30 с.** На PoC-конфигурации (polling 30 с) он не выдерживается: p95 ≈ 31 с. Причина — интервал polling, а не скорость проекции (одно событие проходит конвейер за единицы секунд). Чтобы уложиться, нужно одно из: (а) включить webhook-путь от заглушек для замера и считать p95 по нему (в production webhook и есть основной путь, reconciliation — страховка, см. vision); (б) снизить интервал polling стенда до значения заметно ниже 30 с (например 10–15 с), понимая, что это подгонка под порог; (в) пересмотреть формулировку критерия: «p95 ≤ 30 с при webhook» вместо «при polling 30 с». Выбор — за архитектором и владельцем.
- **Throughput.** ≈ 1,4 события/с на загруженном общем хосте — это разбор очереди одним `ingestion`; во время burst sync lag вырос до 92 с и вернулся к нулю. Для объёма «десятки тысяч активов» первичная загрузка займёт часы, поэтому для production нужен Kafka и параллельные потребители (gap list, п. 1.4). Проекция на целевой объём — оценка по этому одному числу, не замер.
- **Tools.** p95 в диапазоне 0,3–0,7 с на крошечном графе — запас большой, но на реальном графе и без шума от соседнего стенда цифры будут другими.
- **Надёжность.** Ошибок обработки, DLQ и `QUARANTINED` за прогон нет; 0 ошибок из 1000 вызовов tools.

## Ограничения замеров

- Общий хост: соседний стенд Arch RAG держал load average 25–35. Первые вызовы к холодному Neo4j упирались в таймаут запроса 5 с (поэтому в скрипте есть прогрев); в замеры они не входят.
- Граф — seed заглушек плюс 200 объектов burst; формы реального графа (степени узлов, глубина) нет.
- `N=20` даёт грубую оценку p95 (это по сути второе по величине значение), поэтому отличие 30,8 от 31,0 с несущественно; существенно, что значения доходят до ≈ 32 с.
- Клиентский p95 включает TLS-рукопожатия и OIDC-проверку и больше серверного p95 из Prometheus.
- `explain_provenance` не замерен (F4 не вошёл в этот SHA).

## Как повторить

```bash
cd platform/docker
./smoke.sh                                  # стенд поднят с профилем observability, проверки зелёные
scripts/measure.sh | tee measure.md         # N=20 M=200 K=100 P=4 по умолчанию
N=3 M=20 K=10 E2E_JITTER_MAX=2 scripts/measure.sh   # быстрый прогон для проверки скрипта
```

Прогон «источник → граф» занимает около `N` × 30 с, весь `measure.sh` с параметрами по умолчанию — около 15 минут. Код возврата 1 означает, что порог не выдержан или был сбой; детали — в разделе «Провалы» вывода. После вливания F4 повторите прогон: строка `explain_provenance` заполнится, если добавить для неё аргументы в `FIXTURES` внутри скрипта.
